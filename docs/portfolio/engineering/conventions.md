# Engineering conventions

How every app in this repo is built, so the manifesto holds in code and a second app can copy
the first.

## Layout per app

```
apps/<app>/
├── ios/                 # XcodeGen project + <App>Kit package
│   ├── project.yml
│   ├── Makefile
│   ├── Configs/         # *.xcconfig.template committed; real xcconfigs gitignored
│   ├── <App>/           # SwiftUI app target
│   └── <App>Kit/        # domain package: no dependencies, tests run on Linux
├── android/             # Kotlin + Compose, added after iOS ships
└── spec/                # platform-neutral rules + golden fixtures
```

## The domain package (`<App>Kit`)

Same pattern as pensar's `PensarKit` in the private repo:

- **No dependencies.** Not SwiftUI, not HealthKit, not Foundation Models. If domain code
  reaches for a framework, the package stops compiling. That boundary is the point.
- **Plain value types in, plain value types out.** The app adapts HealthKit samples into Kit
  types; Kit computes; the app renders.
- **`swift test` runs on Linux** (CI uses a `swift` container), so scoring changes get feedback
  in seconds without macOS minutes.

## Cross-platform parity through `spec/`

iOS and Android share no code. They share:

1. **A written spec** (`spec/README.md` and the app's engineering docs): inputs, formulas,
   rounding, edge cases.
2. **Golden fixtures** (`spec/fixtures/*.json`): input days plus expected outputs. Both apps'
   test suites load the same files and must match within the stated tolerance.

A formula change is a spec change first: update the spec, regenerate fixtures, then update both
implementations. A fixture is never edited to make one platform pass.

## Data

- **The platform health store is the source of truth.** What the user enters (quick-adds,
  weigh-ins) is written to it, then read back like any other source. Apps keep only derived
  values (trends, estimates, scores) as a cache that can be rebuilt from the store at any time;
  the only app-held data is what the store has no type for (for example a hunger rating), and it
  is included in exports.
- **The cache is excluded from backups and never synced to iCloud.** App Store guideline 5.1.3
  restricts storing personal health information in iCloud (check the current wording before
  each release).
- **Exports are complete** and in open formats (JSON for everything, CSV per table), with a
  version field so imports can migrate.

## AI

- Behind a provider protocol with an `off` implementation that is the default.
- iOS: Apple Foundation Models, guarded by `#available(iOS 26, *)` and the model's availability
  check. When unavailable or off, the AI UI is not rendered at all.
- Prompts receive derived numbers (weekly averages, deltas from baseline), never raw samples.
- No network code anywhere in the AI path.

## Dependencies and SDKs

- **Zero third-party dependencies is the default.** A dependency needs a reason in its PR.
- **Never:** analytics, crash reporting, attribution, ads, remote config, feature-flag services.
  Crashes come from Xcode Organizer / App Store Connect; usage from store analytics.

## Evidence and guardrails

- Every health claim, target and formula is listed in the app's
  `docs/<app>/strategy/science-evidence.md` with its source and strength before it ships.
- Guardrails are domain-package functions with tests, never UI-only checks.
- Estimates carry a range through to the UI.

## Notifications

None in v1. Any later notification is opt-in per type, defaults off, and is listed in Settings.

## Builds and CI

- Projects are generated by XcodeGen; `.xcodeproj` is never committed.
- CI runs the Kit tests on Linux on every change, and a simulator build on macOS for pull
  requests that touch app code. Public repos get GitHub-hosted runners free, but keep macOS jobs
  path-filtered anyway.
- Signing identity (`DEVELOPMENT_TEAM`, profiles) lives in gitignored xcconfigs. Release
  archives are built and uploaded from Shirish's machine with the `asc` CLI (see `ASC.md`) until
  a CI release job is worth the secrets.
